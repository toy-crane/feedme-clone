프런트엔드 캐싱, 레이어부터 다시 그리기

이소정 · blog.example.com

캐싱 전략을 설계할 때 가장 흔한 실수는 "어디에 캐시를 둘까"부터 정하는 것이다. 순서를 바꿔서 "무엇이 얼마나 자주 바뀌는가"부터 물으면 레이어는 거의 저절로 결정된다.

데이터가 바뀌는 속도로 레이어를 나눈다

한 서비스 안에서도 데이터의 변경 빈도는 제각각이다. 상품 가격은 하루에도 여러 번 바뀌지만, 카테고리 트리는 몇 달에 한 번 바뀐다. 이 둘을 같은 TTL로 묶으면 둘 중 하나는 반드시 손해를 본다.

  • 초 단위로 바뀌는 데이터 — 요청 단위 캐시 또는 캐시 없음
  • 분~시간 단위로 바뀌는 데이터 — CDN 엣지 캐시 + 짧은 TTL
  • 거의 바뀌지 않는 데이터 — 빌드 타임 캐시 또는 긴 TTL + 수동 무효화

무효화는 TTL보다 신뢰도가 높다

TTL은 "언젠가는 맞겠지"라는 가정에 기대는 전략이다. 반대로 변경 시점에 명시적으로 캐시를 지우는 무효화는 즉시 반영되기 때문에 사용자가 오래된 화면을 볼 가능성을 크게 줄인다. 다만 무효화 경로를 놓치면 영원히 갱신되지 않는 캐시가 생긴다는 점은 감수해야 한다.

캐시는 "성능을 위한 거짓말"이다. 거짓말의 유통기한을 스스로 정할 수 있을 때만 거짓말을 해야 한다.

실무에서 자주 겪는 함정

가장 흔한 사고는 stale-while-revalidate 설정을 빠뜨린 채 TTL만 짧게 잡는 경우다. 이렇게 하면 캐시가 만료되는 순간 동시 요청이 origin으로 몰려 오히려 장애의 원인이 된다.

결론

캐싱은 하나의 레이어가 아니라 변경 빈도별로 쌓은 여러 장의 필터다. 레이어마다 신선도의 기준을 다르게 두는 순간, 캐시는 더 이상 "맞을 때도 있고 틀릴 때도 있는 도구"가 아니라 예측 가능한 설계 요소가 된다.
